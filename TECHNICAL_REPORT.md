# AlignForge: Technical Report

This document outlines the software architecture, memory optimizations, and novel engineering decisions implemented within the AlignForge pipeline.

## 1. Technical Architecture
AlignForge implements a modular, 4-stage RLHF pipeline designed to operate under strict hardware constraints. The system heavily leverages the HuggingFace ecosystem (`transformers`, `peft`, `trl`).

Key components include:
- `models/base_loader.py`: A unified loader ensuring consistent quantization and dynamic LoRA configuration across Causal LM and Sequence Classification tasks.
- `data/formatting.py`: A strict mapping layer ensuring identical tokenization formatting (Prompt + Response + EOS) during training and evaluation.
- `utils/checkpoint_manager.py`: Centralized logic preventing scattered state management across disparate scripts.

## 2. Novel Engineering Decisions

### 2.1 Unified Tokenization & Formatting
A critical failure mode in many RLHF pipelines is formatting divergence between SFT and Reward Modeling. AlignForge addresses this by routing all string concatenation through `data.formatting.UnifiedFormatter`. This ensures the Reward Model evaluates the exact same token structure generated by the policy model.

### 2.2 Pre-flight Dataset Validation
To prevent "garbage-in, garbage-out," AlignForge features `dataset_validator.py`. It runs a strict pass over the dataset prior to training, calculating truncation percentages and halting execution if empty prompts or malformed conversational turns are detected.

## 3. Memory Optimizations

### 3.1 DPO Reference Model Elision
Traditional DPO implementations load the base model, copy it to create a frozen reference model, and then apply PEFT adapters to the original to act as the policy model. This consumes $2 \times N$ memory, where $N$ is the parameter count.
AlignForge bypasses this entirely. By passing a `PeftModel` directly to `DPOTrainer` with `ref_model=None`, TRL natively disables adapters (`model.disable_adapter()`) during the reference forward pass. **This reduces RAM utilization by roughly 50%.**

### 3.2 Dynamic INT8 CPU Quantization
For the automated evaluation stage, models are dynamically quantized down to INT8 for `nn.Linear` layers (`torch.quantization.quantize_dynamic`). While static quantization is preferred for GPUs, dynamic quantization offers near-instantaneous load times and a 2-3x inference speedup on standard CPUs without a separate calibration step.

## 4. Limitations
- **Sequence Length**: Bounded heavily by CPU RAM; sequences longer than 512 tokens scale quadratically in memory usage without Flash Attention (which requires GPU).
- **Dynamic Quantization Penalties**: Dynamic INT8 introduces slight numerical instability, marginally affecting precision in Reward Model scalar outputs.
